# Как читать проект самостоятельно

Это маршрут чтения, а не список файлов для заучивания. Работайте из корня проекта. Полное объяснение терминов и технологий - в `development-guide.md` и PDF. Для первого знакомства достаточно уверенно читать переменные, условия и методы C#; незнакомые конструкции разбирайте на конкретном запросе.

## Проход 1. Увидеть поведение, 20-30 минут

1. Прочитайте назначение и быстрый запуск в README. Поднимите Compose.
2. В Swagger войдите как Alice и получите список. Сравните с Bob и Support.
3. Создайте заявку. Запишите id, status, ownerId, version. Возьмите её как Support и посмотрите, какие поля поменялись.
4. Добавьте комментарий и закройте. Проверьте запрет редактирования. Откройте снова.
5. Сформулируйте своими словами разницу между 400, 401, 403, 404 и 409. Контроль: знаете ли вы, почему чужая заявка даёт 404?

## Проход 2. Проследить создание, 40-60 минут

1. `src/HelpDesk.Api/Controllers/TicketsController.cs`: найдите `[HttpPost]` и метод Create. Атрибут задаёт HTTP-маршрут. Откуда взят Actor? Почему нет ownerId в параметрах CreateTicketRequest?
2. `Application/Contracts.cs`: входной DTO CreateTicketRequest отличается от TicketDto. Найдите ограничения длины. Это первая проверка формы входных данных.
3. `Application/TicketService.cs`: метод CreateAsync передаёт данные в Ticket.Create. Сервис получает store и clock через конструктор. Найдите место, где данные сохраняются.
4. `Domain/Ticket.cs`: проследите Create -> Edit -> Touch. Где обрезаются пробелы? Где создаётся version? Почему у свойств private set?
5. `Application/ITicketStore.cs`: интерфейс описывает нужные операции, не указывая SQL.
6. `Infrastructure/EfTicketStore.cs`: Add помещает сущность в change tracker, SaveAsync выполняет SQL через EF. До SaveChangesAsync запись в базе ещё не создана.
7. Вернитесь к контроллеру. CreatedAtAction возвращает 201 и Location. Контроль: можете нарисовать путь одного POST без подсказки?

## Проход 3. Разобрать безопасность, 40 минут

1. В `Program.cs` найдите AddIdentityApiEndpoints, AddRoles, UseAuthentication, UseAuthorization, MapIdentityApi. Первое настраивает службы, второе подключает middleware/маршруты.
2. В контроллере `[Authorize]` требует вход, а `[Authorize(Roles = Roles.Support)]` ограничивает take/close.
3. Actor создаётся из подписанного токена, а не из JSON пользователя. Найдите ClaimTypes.NameIdentifier и IsInRole.
4. В `EfTicketStore.Visible` обычный пользователь получает фильтр OwnerId == actor.Id. FindAsync тоже использует его. Поэтому чужая заявка не загружается сервису.
5. В сервисе CommentsAsync сначала вызывает FindAsync. Не переходите сразу к запросу комментариев: именно эта строка проверяет доступ к родителю.
6. Откройте тест OtherUsersTicket_IsHiddenOnEveryAccessibleRoute и прочитайте InlineData. Сопоставьте каждый пример с API-маршрутом.
7. Контроль: если добавить скачивание вложения, где надо проверить доступ к заявке? Ответ: до чтения или выдачи файла, через тот же доступ к родителю.

## Проход 4. Статусы и конкурентные изменения, 40 минут

1. В Ticket прочитайте Take, Close, Reopen. Выпишите предусловие и результат каждого метода.
2. Найдите EnsureOpenForChanges. Он применяется к редактированию и комментариям.
3. В сервисе CheckVersion сравнивает версию клиента с текущей. В DbContext свойство Version помечено IsConcurrencyToken.
4. Это две разные проверки: первая замечает старую форму клиента, вторая - гонку между двумя одновременными запросами после чтения БД.
5. Найдите DatabaseConcurrency_RejectsSecondWriter: два DbContext загружают одну запись, но второй SaveChangesAsync отклоняется.
6. Найдите ApiExceptionHandler: исключения правил и конфликтов превращаются в 409 без внутренних деталей БД.
7. Контроль: почему комментарий тоже вызывает Touch? Чтобы его добавление не прошло незаметно одновременно с закрытием заявки.

## Проход 5. База и запросы, 60 минут

1. `HelpDeskDbContext`: Tickets и Comments - наборы записей. IdentityDbContext добавляет пользователей и роли.
2. В OnModelCreating найдите ограничения длины, внешние ключи, индексы и Version. Сопоставьте со схемой README.
3. `Infrastructure/Migrations/*InitialCreate.cs`: прочитайте только CreateTable Tickets и Comments, затем ограничения и индексы. Designer и ModelSnapshot пока просмотрите бегло: это сгенерированное описание модели для EF.
4. `EfTicketStore.ListAsync`: пройдите фильтр видимости -> status -> priority -> Count -> OrderBy -> ThenBy -> Skip -> Take -> ToListAsync.
5. До ToListAsync это IQueryable: описание SQL-запроса, а не готовый список. CountAsync выполняет отдельный запрос.
6. Найдите AsNoTracking в чтении списков. Сравните с FindAsync: редактирование требует отслеживания сущности.
7. Контроль: почему нельзя сначала ToList, а затем фильтровать? И данные прочитаются лишние, и граница безопасности окажется позже, чем нужно.

## Проход 6. Запуск и инфраструктура, 30 минут

1. Program: сверху вниз службы, затем middleware, маршруты и стартовая подготовка БД.
2. DatabaseSetup: миграции - отдельная настройка; seed выключен по умолчанию. Имена аккаунтов публичны, пароль приходит из конфигурации.
3. compose.yaml: два сервиса, условие service_healthy, два volume. Найдите, какой порт внутри контейнера и какой снаружи.
4. Dockerfile: SDK собирает, runtime запускает. В итоговом образе нет исходников, SDK или тестов.
5. .github/workflows/ci.yml: первый job проверяет SQLite и сборку образа, второй запускает SQL Server и применяет настоящие миграции в тестах.
6. Контроль: что потеряется при down -v? И данные SQL Server, и ключи, которыми защищены токены.

## Проход 7. Сделать небольшое изменение, 1-2 часа

Упражнение A: добавьте новый приоритет, не меняя числовые значения существующих enum. Обновите документацию и тест сортировки. Поскольку enum хранится как int, одна лишь новая константа обычно не требует изменения столбца. Проверьте has-pending-model-changes.

Упражнение B: добавьте поле Category. Измените Domain, DTO, mapping, конфигурацию EF; создайте новую миграцию, не переписывая применённую InitialCreate. Добавьте интеграционный тест сохранения и чтения. Объясните, как старые записи получат значение.

Упражнение C: добавьте фильтр по исполнителю только для Support. Не принимайте ownerId вместо текущей личности и не удаляйте Visible. Напишите тест, что фильтр не расширяет доступ обычного пользователя.

Упражнение D: добавьте тест запрета повторного reopen для уже открытой заявки. Сначала предскажите HTTP-код, затем проверьте.

## Точки остановки в отладчике

Для POST: TicketsController.Create -> TicketService.CreateAsync -> Ticket.Create -> EfTicketStore.SaveAsync. Для чужой заявки: TicketsController.Get -> TicketService.FindAsync -> EfTicketStore.Visible. Для закрытия: CloseAsync -> CheckVersion -> Ticket.Close. Смотрите входные DTO, Actor.Id/IsSupport, ticket.Status/AssigneeId/Version и ChangeTracker в DbContext. Пароли и токены не копируйте в скриншоты портфолио.

Если потерялись, вернитесь к одному запросу и задайте четыре вопроса: какие данные пришли, кто вызывает операцию, какое правило применяется, где выполняется SQL. Не пытайтесь одновременно читать весь Identity или все сгенерированные файлы.
