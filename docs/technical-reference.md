# 1. Задача и результат проекта

HelpDesk API - учебный сервис заявок в техническую поддержку, подготовленный как проект для портфолио начинающего backend-разработчика. Он решает знакомую рабочую задачу: сотрудник сообщает о проблеме, поддержка принимает обращение, обсуждает детали и фиксирует решение. Работодатель может проверить поведение через Swagger UI без отдельного сайта.

Главный результат - не набор CRUD-маршрутов сам по себе, а законченный сценарий с хранением данных, входом, ограничением доступа, понятными ошибками и автоматической проверкой правил. Отдельный фронтенд не разрабатывался по согласованию с заказчиком. Стек задан исходным заданием: C#, .NET 10, ASP.NET Core Web API, EF Core, Microsoft SQL Server, xUnit.

## Участники и основные требования

Обычный пользователь регистрируется, создаёт заявки, видит только свои обращения, редактирует активные заявки, пишет комментарии и открывает свою закрытую заявку повторно. Сотрудник поддержки имеет роль Support, видит все заявки, берёт открытые на себя и закрывает назначенные ему обращения. Публичная регистрация не позволяет выбрать роль.

Заявка содержит название, описание, приоритет, статус, владельца, исполнителя и даты. Приоритеты: Low, Normal, High, Critical. Статусы: Open, InProgress, Closed. Имеются фильтры по статусу и приоритету, сортировка и постраничная выдача. Комментарии связаны с заявкой и автором.

## Что считается готовностью

- Создание возвращает 201 и адрес новой заявки; чтение и изменение возвращают согласованные DTO.
- Пустое название, неверные параметры и неизвестные enum не проходят проверку.
- Попытка прочитать или изменить чужую заявку не раскрывает данные.
- Закрытая заявка не редактируется и не принимает комментарии до повторного открытия.
- Миграция описывает таблицы и связи, а README объясняет запуск с нуля.
- Есть автоматические тесты правил и API, примеры запросов и демонстрационные данные.

В локальной среде выполнены сборка, 41 тест и проверка согласованности миграции с моделью. SQL Server и Docker здесь не установлены: запуск контейнеров и выполнение миграции на настоящем сервере в этой среде не проверены. Для SQL Server подготовлен отдельный job CI с теми же интеграционными сценариями. Наличие workflow в файлах не означает, что он уже был выполнен на GitHub.

## Как пользоваться этим руководством

Сначала прочитайте главы 2-4 и запустите демонстрацию по главе 16. Затем пройдите маршрут чтения кода в главе 17. Главы об инструментах можно читать по мере встречи незнакомых названий. В каждой такой главе разобраны задача, причина выбора, альтернативы и то, что пришлось бы делать без инструмента. Это объяснение уже реализованного проекта, а не обещание будущей разработки.

# 2. Картина целиком: запрос, правила, данные

API - это интерфейс, через который одна программа обращается к другой. Здесь клиентом служит Swagger UI, curl, HTTP-файл или тест. Клиент отправляет HTTP-запрос, сервер проверяет личность и права, выполняет сценарий и возвращает HTTP-ответ с JSON. База данных хранит сведения между перезапусками сервера.

## Разделение ответственности

Controllers отвечают за HTTP и текущего пользователя. Application/TicketService координирует сценарий: найти доступную заявку, проверить версию, вызвать правило, сохранить. Domain/Ticket знает допустимые состояния. Infrastructure/EfTicketStore выполняет запросы EF; HelpDeskDbContext описывает таблицы и связи.

Слои одной сборки разделены папками и интерфейсом ITicketStore. Компилятор не запрещает ошибочную ссылку между папками: границы поддерживает разработчик. При росте их можно выделить в отдельные сборки. Альтернатива без разделения - SQL и правила в контроллере, с повторением проверок в каждом маршруте.

## Один запрос создания по шагам

1. Клиент отправляет POST /api/tickets с JSON и bearer-токеном.
2. Identity проверяет токен; отсутствие входа даёт 401.
3. ASP.NET Core читает CreateTicketRequest и проверяет поля.
4. Контроллер получает Actor из токена и вызывает TicketService.
5. Ticket.Create проверяет правила, создаёт GUID и даты.
6. Store.Add и SaveAsync сохраняют сущность через EF.
7. Контроллер возвращает 201, Location и TicketDto.

# 3. Этапы разработки и принятые решения

## Этап 1. Основная версия

Сначала определены поля заявки, приоритеты, статусы и операции. Изменение статуса выделено в команды take, close и reopen: клиент не может прислать произвольный status через PUT. Список имеет ограниченный размер страницы и фиксированный набор полей сортировки. Это защищает сервер от случайного запроса всех записей и не требует принимать сырые SQL-названия от пользователя.

На этом этапе HTTP-контракт отделён от модели хранения через DTO. Пользователь не задаёт ownerId, assigneeId и даты: эти значения определяет сервер. Для одинаковых значений сортировки добавлен второй ключ Id, чтобы порядок при обычной постраничной выдаче был предсказуемым.

## Этап 2. База данных

Добавлены пользователи Identity, заявки и комментарии. Внешние ключи связывают заявку с владельцем и необязательным исполнителем, а комментарий - с заявкой и автором. EF Core создаёт миграцию InitialCreate. Подготовлен SQL-скрипт docs/schema.sql, который можно просмотреть без запущенной базы.

Удаление пользователя с историей ограничено. Удаление заявки из API отсутствует; на уровне базы удаление строки заявки каскадно удаляет комментарии. Эта настройка не является разрешением на удаление через HTTP.

## Этап 3. Доступ пользователей

Регистрация и вход подключены через готовые Identity endpoints. Роль Support выдаётся через доверенную консоль или демонстрационный seed. Проверка доступа к объекту применяется при каждом чтении или изменении конкретной заявки, включая комментарии. Обычная авторизация маршрута отвечает только на вопрос о наличии входа или роли и не заменяет проверку владельца.

## Этап 4. Правила и тесты

Правила сосредоточены в Ticket: пустой текст недопустим, закрытая заявка доступна только для чтения, назначение возможно только из Open, закрытие - только назначенным сотрудником из InProgress. Добавлена проверка версии на уровне сервиса и базы. Тесты проверяют не только успешные ответы, но и попытки обойти ограничения.

Первая сборка обнаружила уязвимую транзитивную версию System.Security.Cryptography.Pkcs. В проект добавлена явная ссылка на исправленную 10.0.14; проверка NuGet проходит без этих предупреждений. Во время интеграционного прогона найдено несоответствие Content-Type ошибок валидации: декларация общего application/json мешала problem+json. Декларация убрана, после чего контракт ошибок подтвердился тестами.

## Этап 5. Подготовка к показу

Добавлены Swagger, README, .http-примеры, Compose, генерация локальных паролей, smoke-сценарий, pipeline и это руководство. Демоданные содержат двух владельцев и одного сотрудника, три разных состояния заявки и комментарий. Повторный seed не дублирует пользователей и не добавляет заявки, если таблица заявок уже непустая.

Эти этапы описывают логическую последовательность работы. Они не представлены как история отдельных Git-коммитов: новый Git-репозиторий и публикация на GitHub не выполнялись.

# 4. Данные, состояния и права

## Основные таблицы

AspNetUsers хранит учётные записи Identity, включая хеш пароля и служебные признаки. AspNetRoles и AspNetUserRoles связывают пользователя с ролью. Claims, logins и tokens - стандартные дополнительные таблицы Identity; вручную создавать упрощённую таблицу паролей не требуется.

Tickets хранит Id, Title, Description, Priority, Status, OwnerId, AssigneeId, CreatedAt, UpdatedAt, ClosedAt, Version. GUID - уникальный идентификатор, строковые поля имеют максимальную длину, enum сохраняются как int. Version - обычный GUID, обновляемый приложением и помеченный как concurrency token. Это не SQL Server rowversion и не дата.

Comments хранит Id, TicketId, AuthorId, Body и CreatedAt. Вложенные JSON-массивы комментариев в строке заявки не используются: отдельная таблица позволяет независимо читать страницы и проверять связи.

## Переходы состояний

<!-- workflow -->

Take записывает текущего сотрудника в AssigneeId и переводит Open в InProgress. Close требует InProgress и совпадения AssigneeId с текущим Support. Reopen переводит Closed в Open, очищает исполнителя и дату закрытия. История всех прошлых назначений отдельно не сохраняется; это возможное следующее улучшение.

## Политика доступа

| Действие | Владелец | Другой пользователь | Support |
| --- | --- | --- | --- |
| Просмотр и комментарии GET | Свои заявки | 404 | Все заявки |
| Изменение и комментарии POST | Свои активные | 404 | Любые активные |
| Take | 403 | 403 | Открытая заявка |
| Close | 403 | 403 | Своя назначенная InProgress |
| Reopen | Своя Closed | 404 | Любая Closed |

Для чужой и отсутствующей заявки используется одинаковый 404. Это снижает утечку информации через перебор идентификаторов. GUID сам по себе не является защитой: даже если адрес трудно угадать, доступ обязательно проверяется.

## Индексы

Индексы по OwnerId/CreatedAt и Status/Priority/CreatedAt помогают типичным выборкам заявок; по TicketId/CreatedAt - чтению комментариев. Индекс похож на отсортированный указатель к данным, однако занимает место и замедляет изменения. Наличие индекса не означает, что любая комбинация фильтров всегда быстрая: выбор плана остаётся за SQL Server. Реальные планы и нагрузка в этом проекте не измерялись.

# 5. C#, .NET 10, SDK и NuGet

## C#

Задача: выразить данные, бизнес-правила и запросы в проверяемом компилятором коде. C# выбран по заданию и естественно сочетается с ASP.NET Core и EF Core. Классы Ticket и TicketService показывают объектную модель; enum ограничивают набор приоритетов и статусов; record удобен для неизменяемых DTO.

Альтернативы - Java с Spring, TypeScript с NestJS, Python с FastAPI, Go. Все подходят для HelpDesk, но смена языка изменила бы заданный стек и обучающий маршрут. Без C# можно реализовать сервис на другом языке; всё равно понадобятся типы данных, проверки условий, функции и механизм запуска.

Важные конструкции проекта: private set разрешает менять состояние только методам сущности; async Task означает асинхронную операцию; await ожидает её результат; ? помечает допускающий null тип; CancellationToken передаёт отмену. Это не отдельные серверы или фоновые очереди. Асинхронность особенно полезна при ожидании базы, когда поток не должен бездействовать, удерживая ресурсы.

## .NET 10 и ASP.NET Core runtime

Задача: выполнять скомпилированный код, управлять памятью и предоставлять общие библиотеки. .NET 10 выбран исходным требованием. ASP.NET Core - часть платформы для веб-приложений. SDK нужен для restore, build, test, publish; runtime нужен для выполнения готовой программы. Поэтому Docker собирает в образе SDK, а запускает в более узком образе aspnet.

Альтернативы - другая версия .NET либо другая платформа. Здесь net10.0 в csproj фиксирует целевую платформу, а global.json задаёт SDK 10.0.100 с rollForward latestFeature: допускаются более новые feature band SDK внутри 10.0. В среде использовался SDK 10.0.400. Без SDK пришлось бы отдельно вызывать компилятор, собирать ссылки и формировать publish-выход; CLI объединяет эти шаги.

## NuGet и файлы проекта

Задача: получить EF, Swagger и xUnit вместе с зависимостями. NuGet - менеджер пакетов .NET, csproj перечисляет прямые зависимости, packages.lock.json фиксирует разрешённые версии всего графа. Restore --locked-mode проверяет, что зависимость не изменилась относительно файла. При осознанном обновлении пакета сначала обновляют lock обычным restore, проверяют сборку и тесты, затем включают изменения в контроль версий.

Альтернативы - вручную хранить DLL или внутренний feed. Без менеджера потребовалось бы искать совместимые версии, копировать файлы и отслеживать зависимости самостоятельно. Фиксация версий не делает их навсегда безопасными: обновления и проверка уязвимостей остаются нужны.

В приложении Microsoft.AspNetCore.Identity.EntityFrameworkCore, EF Core SqlServer и Design имеют версию 10.0.11; Swashbuckle.AspNetCore - 10.3.1. Тесты используют xunit.v3 4.0.3: v3 здесь часть имени семейства пакетов, а 4.0.3 - опубликованная версия пакета. Полный граф виден в lock-файлах.

# 6. ASP.NET Core Web API и внедрение зависимостей

## HTTP, контроллеры и маршруты

Задача: принять сетевой запрос, разобрать JSON, проверить входные данные и вернуть правильный ответ. ASP.NET Core даёт маршрутизацию, модель запроса, middleware, DI, авторизацию и обработку ошибок. Контроллеры выбраны как явно видимые точки входа для начинающего; встроенные Identity API подключены отдельно через MapIdentityApi.

Альтернативы: Minimal APIs в том же ASP.NET Core, gRPC, GraphQL, другие веб-фреймворки. Minimal APIs были бы уместны и здесь. REST-подобный HTTP API удобен для стандартного клиента и Swagger. gRPC потребовал бы другой контракт и инструменты демонстрации; GraphQL усложнил бы ограниченный сценарий CRUD.

Без веб-фреймворка пришлось бы вручную принимать соединения, разбирать HTTP, сопоставлять маршруты, читать JSON, формировать заголовки и обрабатывать ошибки. Это отвлекло бы от правил HelpDesk. Мы используем обычные GET для чтения, POST для создания и команд, PUT для редактирования доступных полей.

## Middleware: порядок имеет значение

Program.cs сначала регистрирует службы, затем строит приложение и задаёт pipeline. ExceptionHandler оборачивает дальнейшую обработку. StatusCodePages добавляет тело к ответам с кодом ошибки без собственного тела. Routing выбирает маршрут, Authentication устанавливает личность, Authorization проверяет доступ, RateLimiter ограничивает группу Identity. MapControllers и MapIdentityApi добавляют конечные обработчики.

Регистрация Add... ещё не выполняет запрос. Вызовы Use... и Map... определяют обработку во время работы приложения. При чтении Program полезно разделять эти две части.

## DI: зависимости через конструктор

Задача: предоставить TicketService его store и часы, а контроллеру - сервис. Контейнер создаёт нужные объекты и управляет временем жизни. AddScoped означает один экземпляр на scope HTTP-запроса; DbContext также scoped. TimeProvider.System зарегистрирован singleton: этот объект не хранит персональное состояние запроса.

Альтернатива - вручную создавать все объекты через new либо применять сторонний DI-контейнер. Без DI контроллеру пришлось бы знать строку подключения, создавать DbContext и передавать его дальше. Подмена базы в интеграционных тестах была бы труднее. Интерфейс ITicketStore позволяет Application обращаться к возможностям хранилища, не зная конкретного SQL-провайдера.

DI не является автоматической защитой архитектуры и не заменяет понятные интерфейсы. Слишком большой конструктор часто сигнализирует о слишком большой ответственности класса; здесь зависимости небольшие и явные.

# 7. DTO, JSON, валидация и понятные ошибки

## DTO и System.Text.Json

Задача: отделить публичный контракт от внутренних сущностей. CreateTicketRequest принимает только разрешённые поля. TicketDto возвращает результат, не раскрывая внутреннюю модель Identity. System.Text.Json сериализует объекты в camelCase JSON; JsonStringEnumConverter делает enum читаемыми словами и запрещает их числовую форму в JSON.

Альтернатива - отдавать EF-сущности напрямую или использовать другую JSON-библиотеку. Без DTO изменение таблицы могло бы случайно изменить API, а новые setters открыть изменение ownerId/status клиентом. Без сериализатора пришлось бы вручную экранировать кавычки, Unicode и null - это легко сломать. Незнакомые дополнительные JSON-поля игнорируются, но не записываются в доменную модель, что проверяется тестом подмены ownerId/status.

## DataAnnotations и доменные проверки

Задача: быстро отклонить неверную форму входных данных. Required, StringLength, Range и EnumDataType проверяются ASP.NET Core до вызова контроллера. Это даёт 400 с errors. Вторая защита в Ticket проверяет правила даже при вызове кода вне HTTP, например из seed или консольного сценария.

Альтернативы - ручные if в контроллерах, FluentValidation, собственные model validators. Без атрибутов одинаковые проверки и формирование ошибок пришлось бы повторять. При росте сложных взаимосвязанных полей отдельный валидатор может быть удобнее; для коротких DTO атрибутов достаточно.

Лимит JSON-поля проверяется до trim, а доменная модель дополнительно проверяет длину после trim и хранит очищенный текст. Пустая или состоящая из пробелов строка недопустима. API-ошибки формы получают 400; нарушение правила состояния или версии - 409.

## Problem Details и исключения

Задача: вернуть клиенту структурированную ошибку с понятным действием. AddProblemDetails задаёт общий формат; ApiExceptionHandler превращает MissingTicketException в 404, ConflictException и конфликт EF - в 409, RuleException - в 409. Неожиданная ошибка получает общий 500, а подробности пишутся в серверный лог. Ответ содержит traceId, по которому можно связать обращение с журналом.

Альтернатива - собственный envelope вроде {success,error} или повторяющийся try/catch в каждом контроллере. Без общего обработчика легко вернуть разные структуры, забыть HTTP-код или показать строку SQL пользователю. Типовые ошибки 401/403/429 без тела дополняет StatusCodePages. Контракт подтверждён HTTP-тестами, включая Content-Type application/problem+json.

Тексты API сделаны на английском для привычного использования в инструментах; значения и причины объяснены по-русски в документации. Полный контракт приведён в приложении к руководству.

# 8. EF Core, LINQ и доступ к данным

## EF Core

Задача: сохранить C#-объекты в реляционной базе, прочитать их обратно и связать таблицы. EF Core - ORM: он сопоставляет классы таблицам и генерирует параметризованные SQL-запросы. Выбран по заданию и из-за встроенной совместимости с Identity, миграциями и SQL Server.

Альтернативы - ADO.NET с SqlCommand, Dapper, NHibernate. Dapper удобен для полного контроля SQL и простого отображения результатов; ADO.NET даёт низкий уровень. Без EF код сохранения потребовал бы вручную открыть соединение, написать INSERT/UPDATE, создать параметры и восстановить объект из DataReader. Для Identity пришлось бы ещё выбрать готовое хранилище или реализовать нужные stores.

DbContext - объект сеанса работы с данными. Он содержит DbSet и change tracker. После загрузки изменяемой заявки EF помнит исходные значения; SaveChangesAsync находит изменения и отправляет SQL. Add не означает немедленный INSERT. В списках AsNoTracking уменьшает накладные расходы, потому что изменения этих объектов сохранять не планируется.

## LINQ

Задача: выразить фильтры и сортировку в типизированном C#. Where, OrderBy, ThenBy, Skip и Take над IQueryable строят описание запроса. SQL выполняется при CountAsync, ToListAsync, SingleOrDefaultAsync и других операциях получения результата. В store фильтр владельца применяется до чтения списка или конкретного объекта.

Альтернатива - заранее написанный SQL или query builder. Без LINQ запросы можно написать вручную, например:

```sql
SELECT Id, Title, Priority, Status
FROM Tickets
WHERE OwnerId = @ownerId AND Status = @status
ORDER BY CreatedAt DESC, Id ASC
OFFSET @offset ROWS FETCH NEXT @size ROWS ONLY;
```

Параметры обязательны: подставлять пользовательский текст в SQL конкатенацией нельзя. EF помогает параметризацией значений, но не отменяет необходимость понимать результат запроса. Здесь столбцы сортировки выбираются только из enum, а не из введённого имени поля.

## ITicketStore и транзакция

Store содержит конкретные запросы и SaveAsync. Это небольшой специализированный интерфейс, а не универсальный repository для любой сущности. Альтернатива - внедрить DbContext прямо в сервис; это короче, но сильнее смешивает сценарий с деталями SQL. Без store запросы легче размножить и случайно забыть фильтр доступа.

Добавление комментария одновременно меняет Version заявки и добавляет строку Comments одним SaveChangesAsync. EF использует транзакцию для этих связанных изменений: конфликт версии не должен оставить отдельный комментарий после отказа изменения заявки. Для чтения списка count и страница выполняются отдельно; при конкурентной записи они могут видеть немного разные данные.

# 9. SQL Server, связи и миграции

## Microsoft SQL Server

Задача: надёжно хранить пользователей, заявки и комментарии с отношениями. SQL Server выбран исходным заданием и даёт реляционные ограничения, транзакции и совместимый провайдер EF. В Compose используется Developer edition для локальной разработки и показа, не лицензия на промышленную эксплуатацию.

Альтернативы - PostgreSQL, MySQL, SQLite. PostgreSQL был бы сильным вариантом для такого сервиса, но это другой заданный стек. SQLite проще запустить и полезен в тестах, однако отличается типами, SQL-возможностями и поведением конкурентной записи. Без СУБД можно сохранять JSON-файлы, но пришлось бы самостоятельно решать одновременную запись, целостность связей, индексы и откат ошибок.

Первичный ключ определяет запись, внешний ключ проверяет существование связанного пользователя или заявки. OwnerId не может ссылаться на несуществующего пользователя; комментарий не может иметь отсутствующую заявку. Restrict препятствует удалению пользователя с историей, Cascade убирает комментарии при удалении их заявки.

## Миграции EF и dotnet-ef

Задача: воспроизводимо создавать и изменять схему вместе с кодом. InitialCreate содержит Up для создания и Down для обратных действий. ModelSnapshot хранит предыдущую модель для сравнения при создании следующего изменения. Таблица __EFMigrationsHistory в БД отмечает применённые миграции. Подробнее о механизме: [официальное описание миграций EF Core](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/).

Альтернативы - ручные SQL-скрипты, DbUp, FluentMigrator. Без миграций разработчик менял бы таблицы через SQL-команды и отдельно следил, что у каждого окружения та же структура. Миграция не гарантирует сохранность данных сама по себе: её нужно читать, особенно при переименовании и удалении столбцов.

```powershell
dotnet tool restore
dotnet ef migrations add AddCategory --project src/HelpDesk.Api
dotnet ef database update --project src/HelpDesk.Api
dotnet ef migrations has-pending-model-changes --project src/HelpDesk.Api
```

Пример AddCategory показывает будущую работу; выполнять его без изменения модели не требуется. Уже применённую InitialCreate не переписывают для новой функции - добавляют следующую миграцию. В production миграцию лучше выполнять отдельным контролируемым шагом, а не при старте каждого экземпляра приложения. В Compose автообновление включено для удобства одной локальной демонстрации.

## SQL-скрипт и EnsureCreated

docs/schema.sql сформирован командой migrations script --idempotent. Он проверяет историю миграций перед применением соответствующей части; его можно читать и проверять отдельно. Генерация SQL не доказывает успешное выполнение на живом сервере. В SQLite-тестах используется EnsureCreated для быстрой схемы текущей модели; в SQL Server-тестах - MigrateAsync, проверяющий настоящую миграцию. EnsureCreated не заменяет миграции рабочего приложения.

# 10. ASP.NET Core Identity и защита доступа

## Готовая система учётных записей

Задача: регистрировать пользователей, проверять пароли и подтверждать личность следующих запросов. Identity выбран прямо по заданию: он предоставляет UserManager, RoleManager, хранилища EF и готовые endpoint-ы. MapIdentityApi подключает регистрацию, вход и refresh; для заявок используется bearer-сценарий. Общая схема встроенных API описана в [руководстве Microsoft](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-10.0).

Пароли не сохраняются открытым текстом. Приложение передаёт их Identity, а тот хранит проверяемый хеш в своём формате. Настроены длина от 12 символов, уникальный email и блокировка на 5 минут после пяти неудачных входов.

Альтернативы - внешний провайдер OpenID Connect, Keycloak, Microsoft Entra ID, готовый облачный сервис учётных записей. Они полезны при едином входе нескольких приложений. Самописная аутентификация потребовала бы самостоятельно выбрать корректное хеширование, хранение служебных признаков, выдачу и проверку токенов, смену пароля и ограничения входа. Использование готового механизма уменьшает этот объём, однако не отменяет проверку доступа к каждой заявке.

## Токены и роли

Access token действует 30 минут, refresh - 7 дней. Токены Identity в этом режиме opaque: приложение не обещает формат JWT, и вставлять их в JWT-декодер не нужно. Swagger принимает только accessToken и добавляет заголовок Authorization. Data Protection обеспечивает защиту токенов; сохранение ключей между перезапусками важно для их дальнейшей проверки.

Роль Support хранится через Identity. Самостоятельно переданное поле role не повышает привилегии. Выдача роли требует доступа к доверенной консоли и базе. Изменение роли не переписывает старый bearer-токен: войдите заново. Уже выданные access tokens могут сохранять прежние claims до истечения срока. Мгновенный отзыв и одноразовое вращение refresh в проект не добавлены.

## Объектная авторизация

Authenticate означает установить, кто обращается; authorize - решить, можно ли ему выполнить действие. Атрибут Authorize на контроллере требует вход, а Visible в store ограничивает строки по OwnerId. Для Support возвращаются все заявки. Комментарии сначала проверяют доступ к родительской заявке. На take/close дополнительно установлен role-атрибут, а сервис повторно проверяет роль.

Без объектной проверки любой вошедший пользователь смог бы попробовать чужой GUID и получить данные. Тест OtherUsersTicket_IsHiddenOnEveryAccessibleRoute специально обращается к чтению, изменению, чтению/добавлению комментариев и reopen от имени Bob к заявке Alice.

## Границы текущей реализации

Реальная доставка email не подключена. Встроенные дополнительные маршруты Identity присутствуют, но законченный почтовый сценарий не заявляется. Регистрация не требует email confirmation. Rate limit группы Identity - 30 запросов в минуту на IP в памяти процесса. При работе за reverse proxy или в нескольких экземплярах нужны доверенные forwarded headers и подходящая общая политика ограничений.

# 11. Защита от одновременных изменений

Задача: не потерять правку, если два человека открыли одну заявку. Представим, что Alice и Support прочитали одну версию. Support изменил приоритет. Если Alice отправит старое состояние без проверки, она может незаметно затереть его правку.

В проекте каждая мутация требует Version. После успешного изменения клиент получает новый GUID. TicketService.CheckVersion сравнивает присланную версию с загруженной заявкой и возвращает 409 при различии. Клиент должен получить свежие данные и осознанно повторить изменение.

## Почему нужна также проверка базы

Два запроса могут прочитать одну и ту же актуальную версию почти одновременно. Оба пройдут CheckVersion до первой записи. Поэтому Version помечен IsConcurrencyToken: UPDATE EF включает исходную версию в WHERE. Если первый запрос уже сохранился, второй не обновит строку, и EF выбросит DbUpdateConcurrencyException. Обработчик преобразует его в 409. Принцип описан в [документации EF Core по concurrency](https://learn.microsoft.com/en-us/ef/core/modeling/concurrency).

Упрощённая форма SQL:

```sql
UPDATE Tickets
SET Title = @title, Version = @newVersion
WHERE Id = @id AND Version = @originalVersion;
-- Если изменено 0 строк, сохранение конфликтует.
```

## Выбор механизма и альтернативы

Выбран GUID, обновляемый приложением: он одинаково работает в SQL Server и SQLite, а формат виден клиенту. Альтернатива - нативный rowversion SQL Server; он хорош для этого сервера, но в SQLite его поведение пришлось бы имитировать отдельно. Ещё варианты - HTTP ETag/If-Match, блокировки строки, более высокий уровень изоляции или last-write-wins.

Без concurrency token программа могла бы молча принимать последнюю запись. Блокировать строку всё время, пока человек читает форму, неудобно и дорого. Наш подход называется optimistic concurrency: конфликты редки, но обнаруживаются при сохранении. GUID не измеряет порядок правок, поэтому нельзя сравнивать его как дату или счётчик.

Комментарий также меняет Version заявки. Иначе комментарий мог бы добавиться одновременно с закрытием, хотя бизнес-правило запрещает комментарии в закрытой заявке. Одно SaveChangesAsync сохраняет новую версию и комментарий в общей транзакции.

Тест StaleVersion_Returns409AndPreservesLatestData проверяет старую клиентскую версию. DatabaseConcurrency_RejectsSecondWriter использует два DbContext и проверяет защиту непосредственно при записи. Это разные уровни одного ограничения.

# 12. xUnit, интеграционные тесты и тестовая база

## xUnit и Microsoft.Testing.Platform

Задача: автоматически проверять ожидаемое поведение после изменений. xUnit выбран заданием, а версия семейства xunit.v3 работает с современным раннером MTP. В global.json записан runner Microsoft.Testing.Platform. Отдельный пакет TrxReport создаёт машиночитаемый отчёт. Актуальный способ подключения описан у [разработчиков xUnit](https://xunit.net/docs/getting-started/v3/microsoft-testing-platform) и в [документации dotnet test](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-test-mtp).

Fact - один сценарий; Theory с InlineData - один сценарий с несколькими входами; Assert сравнивает результат с ожиданием. Названия методов описывают условие и результат, например ClosedTicket_RejectsEditsAndComments. В каждом тесте важен наблюдаемый эффект, а не совпадение со строкой реализации.

Альтернативы - NUnit, MSTest, TUnit. Без тестового фреймворка пришлось бы писать консольную программу, запускать все проверки вручную, собирать неудачи и формировать отчёт. Проверка только Swagger не даёт повторяемости при каждой правке.

## Два уровня тестов

TicketTests создаёт сущность в памяти и проверяет чистые бизнес-правила без веб-сервера и БД. ApiTests отправляет настоящие HTTP-запросы к приложению, использует Identity для регистрации/входа и проверяет ответы, доступ и сохранение. WebApplicationFactory запускает приложение через тестовый host; схема подхода описана в [официальном руководстве интеграционных тестов ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/test/integration-tests?view=aspnetcore-10.0).

Альтернатива - поднять приложение отдельным процессом и обращаться по TCP. Это полезно для проверки развёртывания, но требует управлять портами и процессами. Без WebApplicationFactory такой запуск и подмена конфигурации стали бы отдельным тестовым кодом. Smoke.ps1 дополнительно предназначен для внешнего запущенного экземпляра.

## SQLite и SQL Server в проверках

По умолчанию каждый интеграционный тест получает отдельную SQLite in-memory базу. Соединение остаётся открытым до завершения теста, затем данные исчезают. Это реляционная база с реальными запросами, связями и change tracking; она даёт больше полезных проверок, чем EF InMemory provider, который не воспроизводит SQL-ограничения.

Альтернативы - SQL Server для всех локальных тестов, контейнеры Testcontainers, общий тестовый сервер. Без лёгкой базы локальные проверки зависели бы от установки SQL Server. При этом SQLite не доказывает корректность всех особенностей SQL Server, поэтому переменная HELPDESK_TEST_SQLSERVER переключает тот же набор на настоящий сервер: создаются временные базы, применяется MigrateAsync, после теста база удаляется.

В тестах Data Protection используется с временным провайдером, чтобы не сохранять ключи на компьютере. Тестовый пароль генерируется на каждый экземпляр теста, а не является готовой учётной записью. IAsyncLifetime управляет подготовкой и очисткой. CancellationToken из TestContext позволяет раннеру отменять долгие операции.

Локально пройден 41 тестовый случай; ошибок и пропусков нет. Число включает варианты Theory, а не только методы. Подробный перечень проверок находится в docs/verification.md.

# 13. OpenAPI, Swagger UI и примеры запросов

## OpenAPI и Swashbuckle

Задача: показать структуру API и дать работодателю возможность выполнить запросы. OpenAPI - машиночитаемый контракт, Swagger UI - интерактивная страница этого контракта. Swashbuckle анализирует маршруты и модели ASP.NET Core и публикует описание и UI. XML-комментарии над методами добавляют краткие пояснения.

Альтернативы - встроенная генерация OpenAPI ASP.NET Core с другим UI, Scalar, NSwag, Postman collection. Здесь Swashbuckle выбран ради привычного Swagger UI, прямо указанного в задании. Без генератора нужно было бы вручную описывать JSON-схемы и поддерживать соответствие всех маршрутов коду. Без UI оставались бы curl и HTTP-клиенты, что менее удобно для быстрого первого показа.

В Development Swagger включён автоматически, в Compose включён флагом HelpDesk__EnableSwagger. В обычном Production конфиге выключен. Authorize принимает accessToken без слова Bearer. Встроенная схема добавляет заголовок ко всем вызовам; анонимные маршруты Identity продолжают работать без токена.

## HTTP-файл, curl и PowerShell

Задача: предоставить повторяемые примеры без написания клиента. docs/requests.http можно открыть в совместимом HTTP-клиенте IDE; подставьте локально password/token/ticketId/version. curl - распространённый CLI-клиент. Smoke.ps1 использует Invoke-RestMethod и выполняет цепочку с проверкой ожидаемых отказов.

Альтернативы - Postman, Insomnia, небольшой собственный клиент. Без этих инструментов понадобился бы сайт или отдельная программа только ради ручного вызова API. HTTP-примеры не являются хранилищем секретов: в них оставлены заменяемые значения, настоящие токены в репозиторий не вставляются.

## Демонстрация поведения

Для показа достаточно войти Alice, создать заявку и записать id/version; войти Support, взять её, добавить комментарий и закрыть; вернуться Alice, получить 409 при редактировании, затем reopen; войти Bob и увидеть 404 на чужой id. На каждой успешной мутации версия меняется. Если забыть скопировать новую версию, 409 будет правильным результатом.

OpenAPI-тест проверяет доступность JSON, UI и основных путей. Он не заменяет ручной визуальный осмотр браузера. Отдельный пользовательский сайт в объём проекта не входит.

# 14. Конфигурация, секреты, часы и журналирование

## appsettings, переменные окружения и user-secrets

Задача: запускать один код с разными адресами БД и секретами. appsettings хранит безопасные значения по умолчанию. Переменные окружения перекрывают их; двойное подчёркивание отделяет секцию, например ConnectionStrings__HelpDesk. user-secrets позволяет хранить локальную строку подключения вне исходников; это удобное хранилище разработчика, а не зашифрованный vault.

Альтернативы - отдельные конфигурационные файлы вне Git, Docker secrets, секреты CI или специализированный vault. Без конфигурационного механизма пришлось бы менять и пересобирать код для каждого окружения; пароль легко оказался бы в коммите. .env читает Compose, а не сам ASP.NET Core при обычном dotnet run. Поэтому для dotnet run нужны env или user-secrets отдельно.

New-LocalSettings.ps1 генерирует криптографически случайные локальные пароли с нужной сложностью. .env исключён из Git и Docker context. Он не перезаписывается повторно. Смена файла не меняет существующие пароли базы и пользователей: эти данные уже сохранены в volume.

## Data Protection

Задача: сохранить ключи защиты opaque-токенов между перезапусками контейнера. Ключи пишутся в api-keys volume через путь /app/keys. Альтернатива - общее защищённое хранилище ключей. Без сохранения новые ключи при пересоздании контейнера могли бы сделать старые токены непроверяемыми. В локальном Compose ключи не шифруются отдельным сертификатом; рабочее развёртывание требует продуманного доступа и защиты ключей.

## TimeProvider, UTC, async и CancellationToken

Задача: единообразно фиксировать время и корректно ожидать БД. TimeProvider передаётся в сервис, что позволяет заменить часы в будущих тестах без изменения правил. Домен принимает конкретное now, поэтому чистые тесты используют фиксированную дату. Без этого каждый метод вызывал бы DateTime.UtcNow сам, усложняя воспроизводимость.

Все даты хранятся как UTC. SQL datetime2 не хранит DateTime.Kind, поэтому при чтении EF-конвертер восстанавливает UTC и JSON возвращает Z. Альтернатива - DateTimeOffset и datetimeoffset, но для общей тестовой сортировки с SQLite потребовались бы дополнительные решения. CancellationToken передаётся из HTTP к запросам EF, чтобы отменённый запрос не продолжал ненужную работу. async/await позволяет ждать I/O без удержания потока; это не делает сами SQL-запросы автоматически быстрыми.

## Логи и health endpoints

Задача: отличить живой процесс от сервиса, который умеет читать рабочую таблицу. /health/live возвращает состояние процесса, /health/ready пробует чтение Tickets и даёт 503 при ошибке. ILogger сохраняет внутреннее исключение для 500 с traceId. Альтернативы - полноценные health checks с отдельными probes и централизованное наблюдение. Без этих средств пришлось бы диагностировать по случайному пользовательскому запросу. Пароли и bearer-токены приложение специально не печатает.

# 15. Docker Compose и GitHub Actions

## Dockerfile и Compose

Задача: дать работодателю одинаковый способ поднять API вместе с SQL Server. Dockerfile собирает приложение в SDK-слое и копирует publish-выход в runtime-слой. API запускается от непривилегированного пользователя образа. Compose описывает два сервиса, сеть, переменные, порты, volumes и ожидание готовности БД. Принцип модели сервисов и volumes изложен в [документации Docker Compose](https://docs.docker.com/compose/intro/compose-application-model/).

Хост обращается к localhost:5080; внутри API слушает 8080. В строке подключения контейнера имя сервера db означает сервис Compose, а не localhost. SQL Server публикуется на 14333 хоста и 1433 внутри. Порты привязаны к 127.0.0.1 для локальной демонстрации. SQL healthcheck выполняет SELECT 1; только после его успеха стартует API, который мигрирует схему и запускает seed.

Альтернативы - ручная установка SDK и SQL Server, локальные службы, .NET Aspire или другое окружение контейнеров. Без Compose понадобилось бы отдельно создать сеть/volumes, поднять БД, дождаться готовности, собрать API и передать ему настройки. Compose сохраняет эти решения в одном файле. Он не обеспечивает автоматически HTTPS, production-секреты, резервное копирование или высокую доступность.

## Volumes и версии образов

sql-data хранит БД; api-keys - ключи токенов. docker compose down останавливает контейнеры, но сохраняет named volumes. down -v удаляет их и является сбросом данных. Образы SDK/aspnet 10.0 и SQL Server 2022-latest имеют изменяемые теги; для воспроизводимого рабочего релиза можно дополнительно закрепить digest, периодически обновляя его после проверок.

SQL Server Developer подходит для разработки и тестирования. Образ требует x86-64 окружения и достаточной памяти Docker. Docker в исходной среде не установлен, поэтому здесь не заявляется проверенный запуск образа. Workflow содержит docker build и отдельную SQL-проверку для последующего реального запуска на GitHub.

## Git, GitHub Actions и CI

Задача: хранить изменения проекта и проверять их независимо от компьютера автора. .gitignore исключает .env, сборочные файлы и локальные результаты. GitHub Actions описывает CI как workflow с jobs и steps, что объяснено в [официальной документации GitHub](https://docs.github.com/en/actions/get-started/understand-github-actions).

Первый job восстанавливает зафиксированные зависимости, собирает Release, запускает тесты на SQLite, сохраняет TRX и собирает Docker image. Второй job запускает SQL Server с новым случайным паролем, маскирует его в журнале и выполняет тесты с реальными миграциями. Каждому тесту выдаётся отдельная временная база. После выполнения SQL-контейнер удаляется.

Альтернативы - GitLab CI, Azure Pipelines, Jenkins, локальный скрипт. Без CI нужно было бы вручную повторять сборку и тесты после каждого изменения и доверять окружению автора. Без Git можно пересылать архивы, но трудно сравнивать версии и связывать изменение с причиной. Публикация репозитория и первый запуск workflow остаются действием владельца проекта; подключённый GitHub-аккаунт для разработки не требовался.

# 16. Запуск, демонстрационные данные и диагностика

## Рекомендуемый запуск

Установите Docker Desktop с Linux containers и Compose v2. Откройте PowerShell в папке проекта. SDK .NET на хосте для контейнерного способа не требуется.

```powershell
powershell -ExecutionPolicy Bypass -File scripts/New-LocalSettings.ps1
docker compose up --build -d
docker compose ps
```

Первый запуск может занять несколько минут на скачивание образов и старт SQL. Дождитесь ответа 200 на http://localhost:5080/health/ready и откройте http://localhost:5080/swagger. Если порт уже занят, измените API_PORT или SQL_PORT в локальном .env до запуска и используйте новый адрес.

Alice имеет две заявки, Bob - одну, Support видит три. Все демонстрационные пользователи используют HELPDESK_DEMO_PASSWORD из .env; SQL_SA_PASSWORD - другой пароль для подключения БД. Проверка скриптом:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/Smoke.ps1
```

Скрипт добавит ещё одну заявку и проверит полный цикл. На Linux/macOS используйте pwsh либо создайте .env из примера вручную. Не используйте реальные рабочие пароли для демонстрации.

## Запуск без Docker

Нужны SDK .NET 10 и работающий SQL Server/LocalDB. Значение по умолчанию - LocalDB с Windows Authentication. LocalDB - отдельная установка; наличие .NET не означает наличие SQL Server. Для другого сервера задайте ConnectionStrings__HelpDesk в терминале либо user-secrets. .env обычный dotnet run автоматически не читает.

```powershell
dotnet restore HelpDesk.sln --locked-mode
dotnet tool restore
dotnet ef database update --project src/HelpDesk.Api
dotnet run --project src/HelpDesk.Api
```

Демоданные в обычном конфиге выключены. Если нужны примеры, до dotnet run задайте HelpDesk__SeedDemo=true и HelpDesk__DemoPassword со своим сложным паролем. База уже должна быть мигрирована. Создавать Support публичным API нельзя: после регистрации выполните dotnet run --project src/HelpDesk.Api -- --grant-support agent@example.test и войдите заново.

## Частые проблемы

| Симптом | Что проверить |
| --- | --- |
| docker не найден | Установлен и запущен ли Docker Desktop, доступен ли CLI |
| SQL healthcheck не проходит | Логи db, память Docker, x86-64, сложность пароля |
| Ошибка входа после смены .env | Пароли уже созданных пользователей и volume не меняются от файла |
| 401 на заявках | Токен accessToken, срок действия, Authorize, отсутствие лишнего Bearer в поле UI |
| 403 на take/close | Роль Support и новый вход после её выдачи |
| 404 на известном id | Это может быть чужая заявка; проверьте текущего пользователя |
| 409 после комментария | Комментарий тоже обновил version; скопируйте новый GUID |
| 409 при редактировании | Проверьте status: Closed нужно сначала reopen |
| 503 readiness | Есть ли соединение и таблица Tickets, применены ли миграции |
| Ошибка --logger trx | Проект использует MTP: нужен --report-trx, см. README |

Диагностика Compose: docker compose logs api db. Остановка с сохранением данных: docker compose down. Намеренный полный сброс: docker compose down -v; эта команда удалит и данные, и ключи. Для типичного перезапуска сброс не нужен.

# 18. Практика: безопасно изменить проект

## Пример нового поля Category

Задача: добавить категорию обращения, например Hardware/Software/Network. Сначала определите правило: обязательна ли категория, какие значения допустимы, что станет со старыми записями. Затем добавьте свойство и проверку в Domain, разрешённое поле в Create/Edit DTO, ответ в TicketDto и mapping. После этого настройте EF, создайте новую миграцию и проверьте сгенерированный Up.

Если поле обязательно, миграция должна дать старым строкам допустимое значение или выполнить заполнение. Простое добавление NOT NULL без решения для старых данных может сорвать обновление. Изменение DTO не изменяет таблицу автоматически: требуется модель EF и миграция. Изменение таблицы вручную не обновляет ModelSnapshot.

Проверьте создание и последующее чтение категории, неверное значение и редактирование закрытой заявки. Существующие тесты прав должны продолжить проходить. Обновите .http-пример, Swagger-комментарии при необходимости и руководство. Это небольшое упражнение проходит через все слои и хорошо показывает их ответственность.

## Пример нового маршрута вложения

Не начинайте с выдачи файла по его идентификатору. Сначала найдите связанную заявку и проверьте доступ текущего Actor тем же способом, что для комментариев. Только после этого читайте файл из хранилища. Добавьте тест: Bob не скачивает вложение заявки Alice. Позже понадобятся лимит размера, типы файлов и отдельное хранилище; включать большие бинарные файлы в DTO заявки не стоит.

## Рабочий цикл изменений

1. Сформулируйте ожидаемое поведение и его HTTP-результат.
2. Найдите маршрут, сервис, правило и место сохранения по справке чтения.
3. Измените минимальный набор связанных файлов.
4. Добавьте тест нового важного поведения и выполните имеющиеся проверки.
5. Проверьте миграцию и README, если меняется запуск или контракт.
6. Посмотрите diff и убедитесь, что туда не попали .env и токены.

```powershell
dotnet build HelpDesk.sln -c Release
dotnet test --solution HelpDesk.sln -c Release --no-build
dotnet ef migrations has-pending-model-changes --project src/HelpDesk.Api
```

# 20. Проверки, ограничения и следующий шаг

## Фактическая локальная проверка

В среде Windows с SDK 10.0.400 собрана конфигурация Release с TreatWarningsAsErrors: ошибок и предупреждений нет. 41 тест выполнен, 41 пройден, пропусков нет. Проверка EF has-pending-model-changes не обнаружила отличий от InitialCreate. Идемпотентный SQL-скрипт создан. Зависимости восстановлены с lock-файлами; при восстановлении исправлена известная уязвимая транзитивная библиотека.

Интеграционные проверки выполнялись на SQLite in-memory. Настоящий SQL Server, Docker Compose и внешний smoke-сценарий в исходной среде не запускались: нужных служб нет. Подготовленные Dockerfile и workflow требуют первого реального контейнерного прогона на компьютере с Docker или после публикации в GitHub. Генерация SQL и прохождение SQLite не заменяют этот прогон.

## Что понадобится для рабочего развёртывания

Compose намеренно удобен для локального показа: он включает seed и Swagger, мигрирует при старте и использует sa для БД. Для рабочего сервера выделите ограниченную учётную запись приложения, выполняйте миграции отдельной процедурой, отключите демоданные, настройте HTTPS и защищённое хранение ключей. Добавьте резервное копирование и наблюдение под реальные требования эксплуатации.

Не подключены реальная доставка email и готовый процесс восстановления через почту. Access token нельзя мгновенно отозвать публичным API; refresh не одноразовый. Лимитер находится в памяти одного процесса. Отсутствуют история изменений, переназначение, удаление, SLA, поиск по тексту и вложения. Это контролируемый объём небольшой программы, а не недоделанные обещанные экраны.

## Порядок дальнейших улучшений

Сначала выполните настоящий Compose/SQL Server прогон и сохраните результаты CI. Затем добавьте аудит переходов состояния: кто, когда и из какого статуса перевёл заявку. После этого - SLA и уведомления, если появятся требования. Расширяйте архитектуру по мере роста, когда конкретная зависимость мешает тестам или работе команды, а не только ради большего количества проектов.

## Как был подготовлен PDF

Задача: получить читаемое руководство на русском, которое можно сохранить и открыть без редактора Markdown. Исходники находятся в docs/development-guide.md, reading-map.md и api.md. Python-скрипт build_docs.py собирает их через ReportLab, встраивает кириллические шрифты, добавляет оглавление, схемы, номера страниц и ссылки. Это вспомогательные инструменты документации, а не зависимости HelpDesk API.

Альтернативы - Word/LibreOffice с экспортом PDF, Pandoc/LaTeX, HTML-печать браузера. Без программной генерации пришлось бы вручную переносить изменения текста, оглавление и нумерацию в отдельный редактор. Для визуальной проверки использованы Poppler/pdftoppm и извлечение текста PDF; они помогают обнаружить обрезку и отсутствующие символы. Для пересборки нужен ReportLab и доступный шрифт с кириллицей; инструкция и зависимости есть в README.
